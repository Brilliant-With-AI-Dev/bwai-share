Date: 2026-08-23
Decision scope: Product and architecture direction only. This is not a migration plan.
Recommendation: Re-conceive Agentic Mirror as the next evolution of the existing Brilliant Mirror experience, not as a second product. Preserve /mirror, the Letter, historical Action Plans, and the report/chat surface while importing Agentic Mirror's deeper evidence, user-control, frozen-context, versioned-review, and acceptance model. Prefer a narrowly scoped, Brilliant-owned canonical data authority for new sensitive Mirror runs, contingent on proving its full erasure and stateless-inference contracts. Do not make persistent Core chat or flat ContextAssets canonical unless Core first proves the deletion, audit, and lifecycle guarantees Brilliant's own product policy requires. Decide request-bound versus durable-worker execution separately from storage ownership.

Executive decision

The concept belongs in Brilliant Apps. Agentic Mirror's real product advance is not its local launcher, SQLite schema, generic workflow generator, or multi-pane workspace. It is a trustworthy path from incomplete context to an accepted artifact:

bounded evidence → explainable sufficiency → human-authorized transition → frozen generation truth → versioned artifact → user-approved review → explicit acceptance

That nucleus strengthens Brilliant Mirror's intended role as an onboarding ritual that produces durable insight and eventually leads into XO. Brilliant already has intake, an adaptive interview, staged Letter/Action Plan generation, a durable report, and grounded follow-up chat; the explicit review-and-acceptance stage would be new. The right disposition is therefore evolve in place, with substantial internal replacement allowed, rather than wholesale product replacement or permanent coexistence. XO itself remains directional and is not a current production handoff (release status, XO direction).

The preferred architecture candidate is Option B, a companion-owned canonical Mirror runtime, because the sensitive transcript, evidence ledger, frozen generation packet, revisions, and later profile proposals form one governed lifecycle. Current Core persistence can support the experience mechanically, but the repository confirms that it cannot presently prove hard deletion of task conversations or ContextAssets, supplies no native transaction/CAS semantics, and lacks the governed audit contract Brilliant says durable profile data requires. A queue layered over Core would not fix that; the smallest coherent external boundary must own the canonical content lifecycle and its deterministic transition/recovery rules. A separate durable worker is optional and should be selected only if failure testing proves request-bound execution inadequate.

This recommendation is deliberately narrow. It is an exception to Brilliant's accepted Core-first architecture, not a proposal for a new general platform or a second workflow interpreter. Under the current binding trust policy, the native approach is appropriate only for synthetic, ephemeral, or explicitly non-production validation; disclosure alone does not satisfy the hard-erasure promise. Native would become the preferred production architecture if Core closes the specific governance and lifecycle gaps listed below, or if the user explicitly amends the governing product policy.

Decisive reasons

  1. Product fit is already strong. Brilliant describes Mirror as an approximately 45-minute interview producing a Letter and Action Plan, with the route sequence start → form → interview → generation → report (Mirror context). Agentic Mirror can add a review-and-acceptance stage while preserving that route shell and overall journey.
  2. Evolution preserves the valuable surface and installed product meaning. /mirror/* is the repository's live product route, while the current return surface already loads durable artifacts and recovers incomplete generation (route status, report recovery).
  3. The trust contract is more demanding than the current native store. Brilliant promises hard deletion of the profile and derived artifacts and calls for user-visible access logs (product vision). The current deletion runbook says the underlying Core task/conversation has no deletion API and can retain verbatim interview answers (deletion runbook).
  4. Agentic Mirror's value is inseparable from durable state semantics. Its implementation persists stage decisions, distillations, frozen snapshots, artifact versions, review decisions, corrections, and acceptance in a transactional SQLite model (workflow store). Reproducing those guarantees over a flat overwrite store would move database responsibilities into application code.
  5. A narrow companion can respect platform locality. Brilliant already centralizes AI behavior behind an AiGateway/AiTransport seam (AI gateway), and a proposed—but unratified—Team Mirror design independently identifies a narrow relational control plane when Core lacks required coordination semantics (Team Mirror proposal). Whether that boundary executes work in-request or through a durable worker is a separate decision.

What is valuable in Agentic Mirror

Confirmed product logic

Agentic Mirror is a local, accountless, human-governed evidence-to-artifact system. Its models receive role-specific bounded snapshots and can propose questions, transitions, generation, and review; deterministic application code validates and commits consequential state through createPublicWorkflowInterface (composition seam, bounded snapshots, integrity validation).

The valuable behaviors are:

  • The system develops context before drafting instead of treating the first prompt as sufficient.
  • Evidence is associated with requirements, provenance, confidence, and conflicts.
  • The model may recommend a stage transition, but the user authorizes advancement and completion.
  • Completed stages produce durable distillations; final interview completion creates a frozen, versioned generation snapshot.
  • Provisional model output is distinct from canonical state.
  • Review produces material recommendations without authority to mutate or accept the artifact.
  • Users approve, reject, or annotate recommendations; approved changes produce a new artifact version.
  • Completion requires explicit artifact acceptance, not merely a model verdict.
  • Corrections supersede prior evidence and can invalidate downstream artifacts rather than silently rewriting history.
  • Cross-run context can compound through provenance, supersession, correction, and later reuse; the persistence and approval policy is replaceable, but that compounding value is not.
  • Recovery, export, and deletion are treated as part of product trust, not operational afterthoughts.

The source makes those authorities explicit: the Interview model is limited to one focused question or a recommendation and cannot change state (Interview model); Generation receives frozen authority (Generation model); Review can recommend but not mutate or accept (Review model); and acceptance is a separate workflow action (public interface).

Implementation-specific machinery to leave behind

The following are adapters or product choices, not essential value:

  • accountless local-only deployment, the macOS launcher, and browser-opening process;
  • a user-supplied Gateway key, model picker, and local hard-dollar workflow cap;
  • SQLite's exact normalized schema, WAL files, local backup rotation, and process-global lease;
  • the generic user-facing workflow-definition language and support for many arbitrary writing workflows; per-run tailoring of Mirror's requirements and completion rubric should remain;
  • the exact Grounding/Shaping phase names and five-pane workspace layout;
  • NDJSON-over-localhost transport and developer recovery diagnostics;
  • automatic, ungoverned global profile writes; provenance-bearing cross-run context remains essential but must adopt Brilliant's approval and erasure rules.

The generic workflow-studio portion should not be smuggled into Mirror. Brilliant's product vision assigns data-defined workflows to Reflow and describes Mirror as the onboarding ritual that seeds XO and the Leadership Profile (Reflow, Mirror direction).

Current Brilliant Apps reality

Confirmed platform capabilities

Brilliant already supplies most of the visible experience skeleton, but not the requested independent review-and-acceptance stage:

  • The route graph covers intake, interview preparation, interview, generation, and report (Mirror context).
  • One Core task is the durable interview conversation, while Mirror stores only a thin app-state snapshot and reconstructs chat from task history (state snapshot).
  • The current deliverable coordinator has an internal generation sequence—reasoning, Letter part one, complete Letter persistence, then Action Plan persistence—which is not the same as the proposed four-stage user experience (inline deliverables).
  • Finished artifacts use per-run value keys and a manifest-last publication pattern so partially written state is not presented as complete; re-posting the same run key overwrites in place (return persistence).
  • The report surface includes grounded post-report chat whose messages are persisted by Core. It has no completion/advance state and does not yet constitute an XO handoff (ChatPanel).
  • Capability code receives AI, artifacts, context, authentication, flags, telemetry, and clock through typed seams; live AI calls are centralized behind ctx.ai (capability context, server wiring).

Stytch has a precise, limited role: it verifies human sessions, supplies organization/member identity, and mints M2M credentials for server-to-Core calls (auth context). Browser code does not receive Core credentials. Stytch is not the artifact store, conversation store, orchestration engine, or model runtime.

Other existing external-service boundaries—Deepgram, Stripe, Resend, Edge Config, Upstash, and Core—are typed, server-local adapters for specific concerns. Their existence demonstrates that Brilliant Apps is not literally dependency-free, but none provides a general relational product database. The app dependency set has no SQL driver or ORM (web package); the root Upstash client is a narrow server-side KV seam (KV client).

Confirmed constraints

The accepted architecture direction is Core-first: apps contain product modules, shared engines are singular, durable user data is intended to become governed ContextAssets, and Mirror should converge only after shared workflow primitives reach parity (architecture spine). A separate Neon-backed path is allowed for prototypes or client handoff, not established as the production default (stack direction).

Current Core primitives are useful but shallow:

  • visible chat messages persist, while other generated data is stream-only unless explicitly stored (M2M pattern);
  • ContextAssets are flat overwrite records; the SDK layers immutable version keys and manifests over them (versioning);
  • Mirror itself documents that the platform has no delete verb and therefore uses tombstones (state snapshot);
  • ContextAssets do not supply transactions, compare-and-swap, atomic multi-record publication, or a native audit ledger (facet-model ADR);
  • model selection and generation parameters cannot be changed per request through current prompt overrides (M2M pattern);
  • dynamic recursion, fan-out, arbitrary tool execution, and durable wait/resume are not confirmed current platform capabilities; fetch-tool and fan-out are reserved/rejected today, while the broader patterns document is explicitly not a commitment (architecture spine, future patterns).

Most importantly, the governance gap is explicit rather than hypothetical. The accepted product vision requires hard deletion and transparent access, while the current runbook says no API deletes the canonical Core interview conversation and warns against claiming otherwise (product vision, deletion gap). The facet-model ADR is Proposed, not authorizing, and concludes that production Leadership Profile persistence must wait for verifiable erasure and a user-visible audit ledger (facet-model status, erasure requirement). The accepted architecture spine independently blocks Leadership Profile storage work until the governing contract lands (architecture spine).

Contrary native recommendation already in the repository

A directly relevant 2026-08-18 document recommends user-scoped Core ContextAssets with one governed Runtime writer and no second production data system (continuous-profile recommendation). That is the strongest documented case for Option A: it follows the accepted stack, partitions provenance, layers immutable records and manifests, and centralizes serialization/recovery in Runtime.

This memo does not silently override it. The document is marked Proposed and explicitly authorizes no persistence or rollout (status); it also keeps production writes disabled until erasure, audit, protected-write, tenancy, identity, and isolation prerequisites are proven (production boundary). Its recommended Core-backed writer is coherent only after those prerequisites exist. Under today's confirmed transcript-deletion gap, it cannot make persistent Core chat the canonical sensitive content plane. That is why this memo prefers Brilliant-owned canonical authority while preserving Core-plus-governed-Runtime as the leading architecture if Core closes the gap.

Production status caveat

The route is live, but source contains independently gated return, transcript-rebuild, inline-generation, and continuous-conversation paths. Default flag configuration is not proof of the current production Edge Config state. This memo therefore treats the existing code as demonstrated platform capability, not as a claim that every path is enabled for every production user.

Option A — native Brilliant Apps

Architecture intent

Use only existing Brilliant Apps capabilities: the current /mirror product module, Stytch authentication, Brilliant server routes, the sanctioned SDK/Core AI path, Core task history, ContextAssets, capability modules, and current report/chat surface. Introduce no new backend or database.

This is not a stripped-down option. Its strongest form retains the complete four-stage experience and reproduces the important Agentic invariants through explicit schemas, immutable keys, manifests, fences, and user decisions.

Conceptual end-to-end flow

  1. Basic information intake. The authenticated user starts or resumes a Mirror run. The existing owner-stamped browser envelope holds transient form progress; a thin mirror/state snapshot records the run ID, task ID, asserted intake facts, and current stage. Intake produces an internal evidence-coverage contract rather than a generic workflow definition.
  2. Interview. One Core task remains the canonical conversation. The app injects a bounded Mirror interview contract and reconstructs the session from Core history. After each answer, deterministic application logic updates an evidence/conflict projection and asks one focused next question. The model may recommend advancement; the user chooses whether to continue, revisit a topic, or approve the transition. Each approved stage writes an immutable distillation plus a newer manifest pointer.
  3. Deliverable generation. Explicit interview completion first writes a durable finished marker and an immutable generation packet. Bounded capability calls then produce the Letter and the currently configured post-Letter artifact; today that is the Action Plan, while the continuous redesign leaves its successor open. Each completed artifact version is written under a new key, read back where required, and published by updating its manifest last. Partial generation remains resumable and invisible as a finished report.
  4. Deliverable review and chat. /mirror/report loads the published version. A separate bounded review capability returns only material suggestions. The user can inspect as deeply as desired, steer revisions in plain language, approve a compact change set, or accept the current artifact; approved changes generate a new version. Grounded report chat continues through Core. A later XO handoff may consume the accepted artifacts, but that is directional future behavior rather than current capability.

Native state and data lifecycle

Lifecycle layer Canonical responsibility
React/local UI state Typing, streaming fragments, panel state; disposable.
Owner-stamped session envelope Cross-step browser handoff and optimistic resume hints; never the durable final source.
Core task history Canonical interview and post-report conversation.
ContextAsset run records Thin run projection, evidence/coverage ledger, immutable stage distillations, frozen generation packet, artifact/review versions, acceptance record, and latest manifests.
Governed profile No automatic profile write. At most, retain run-scoped profile proposals until the protected-write and erasure contract exists.

Each consequential write is append-then-publish: write a unique immutable value, verify it when needed, then overwrite the small manifest/pointer. Fences and idempotency keys prevent stale retries from winning. Recovery reads the finished marker, manifest, immutable values, and Core history to select the last complete state. A user correction creates a newer fact/evidence version and marks dependent output stale; it does not rewrite history.

The lifecycle is mechanically feasible because current Mirror already uses thin snapshots, fenced intake-state revisions, finished markers, and values-first/manifest-last artifacts. Current completed artifact keys are unique per run but overwrite in place when the same run key is re-posted; immutable artifact/review versions would be new Option A machinery (return persistence). It remains application-emulated transactional behavior. Concurrent or partially failed writes can be detected and repaired, but not atomically committed as one database transaction.

Native strengths

  • Lowest incremental build and operating burden.
  • Preserves the accepted Core/SDK architecture and central observability path.
  • Reuses the live route, current Stytch/Core delegation, report, chat, recovery, and artifact modules.
  • Avoids a new database vendor, migrations, backup policy, service credentials, and on-call surface.
  • Lowest replacement and historical-compatibility risk.
  • Makes capability improvements available to the existing platform without a parallel runtime.

Native constraints and costs

  • The canonical transcript remains in a store Brilliant currently cannot verifiably erase through its API.
  • Flat ContextAssets force the app to own versioning, manifests, fences, reconciliation, scans, and multi-write failure handling.
  • Durable Leadership Profile writes remain blocked by governance requirements.
  • Long generation/review sequences are tied to browser/server request lifetimes unless broken into manually recoverable operations.
  • Core's model configuration, retention, payload, pagination, durability, and pricing contracts are not fully established in this repository.
  • Reliability is recoverable-at-least-once rather than transactional exactly-once; a crash after model completion but before checkpointing may repeat an inference call.

When Option A is the superior choice

Under the current trust policy, Option A is superior for synthetic, ephemeral, or explicitly non-production product validation: it tests the interview, review, and acceptance experience with the least new machinery. It is not a compliant production choice merely because Core retention is disclosed. It becomes the preferred production option if Core adds the deletion, audit, transaction/durable-operation, and data-handling guarantees in the “conditions” section, or if the user explicitly changes the governing product promise with appropriate legal and trust review.

Option B — companion-owned Mirror runtime

Architecture intent

Keep Brilliant Apps as the only user-facing application and Stytch as the identity authority, but place authoritative sensitive Mirror state behind one private, purpose-built MirrorRuntime boundary. The runtime owns a managed relational database and code-authored lifecycle coordination. It may be deployed separately or initially colocated behind Brilliant's server routes; deployment topology is secondary to canonical ownership.

The smallest coherent external boundary owns together:

  • interview transcript and run events;
  • evidence, conflicts, stage decisions, and frozen generation packets;
  • artifact, review, correction, and acceptance versions;
  • profile proposals and user decisions, if approved;
  • idempotency, transition checkpoints, retries, and recovery; leases belong here only if asynchronous workers are selected;
  • access audit, retention, export, deletion inventory, and deletion verification;
  • stateless AI calls whose sensitive prompts and responses are not appended to persistent Core chat.

A database-only companion while Core still owns persistent conversation content is incoherent: it creates two authorities and cannot delete the canonical transcript. An execution-only queue is also insufficient: it improves retries while leaving privacy and erasure unchanged. Canonical content and deterministic lifecycle transitions therefore belong behind one deep boundary.

Two decisions must remain separate:

  1. Canonical content authority: Core versus a Brilliant-owned database. This memo recommends the Brilliant-owned authority, contingent on its governance proof.
  2. Execution topology: request-bound server execution versus a durable asynchronous worker. Agentic Mirror itself does not prove a durable worker requirement; it uses a process-local lease, bounded retry state, and explicit replay (generation lease, retry path). Select a worker only if termination/resume tests or product latency requirements justify its operational cost.

Conceptual end-to-end flow

  1. Basic information intake. A Brilliant server route verifies the Stytch session and resolves a stable owner subject. It creates or resumes a run through MirrorRuntime; the database transaction records intake assertions, consent/policy version, and the initial evidence-coverage contract. The browser receives only an opaque run ID and presentation state.
  2. Interview. Each user message becomes an append-only run event scoped to the owner. The runtime builds a bounded model snapshot from accepted evidence and current stage, invokes AI through a stateless adapter behind Brilliant's existing AI-gateway abstraction, records the resulting proposal, validates it deterministically, and commits the canonical assistant turn and coverage changes. User-approved stage transitions transactionally write the decision and immutable distillation. Durable events stream back to the browser; reconnection resumes from an event cursor.
  3. Deliverable generation. Explicit completion transactionally creates a frozen generation packet and an idempotent operation record. Request-bound execution may perform the bounded calls and checkpoint each result. If validation proves tab-independent execution necessary, a worker can instead lease that same operation and resume from the last committed checkpoint. The runtime stores immutable Letter and post-Letter artifact versions plus usage metadata in either topology.
  4. Deliverable review and chat. The report route reads the accepted or latest reviewable version from the runtime. Review proposals, revision decisions, and accepted versions are first-class records, but the UI can remain plain-language and low-friction. Follow-up chat is grounded in accepted artifacts and stored in the same governed owner scope. A future XO integration receives only explicitly approved profile proposals or policy-safe derived context.

Companion state and data lifecycle

The database holds append-only events and immutable content versions, with relational current-state projections for efficient reads. Every row carries owner, run, provenance, schema/policy version, and timestamps; consequential commands carry idempotency keys. Stage and artifact transitions occur inside transactions. Operations have attempt records and terminal outcomes; leases and heartbeats are added only if asynchronous execution is selected. The user-facing report points only to committed, published artifact versions.

Deletion is a product command, not a manual database edit. It resolves all owner-linked run content, transcripts, artifacts, reviews, derived profile proposals, caches, indexes, and provider references; blocks new writes; performs the defined erasure or cryptographic-erasure procedure; and records non-content verification evidence. Exact backup expiration and external model-provider deletion cannot be asserted until contracts are chosen, so those remain explicit launch validations rather than assumed guarantees.

Core is optional downstream infrastructure in this option. It may receive opaque identifiers or an explicitly approved, policy-safe derivative when its governance contract permits. It must not receive the only copy of sensitive content or silently persist prompts/responses. If Core later supplies a verified non-persistent inference mode, it can serve as the stateless AI transport; otherwise the runtime uses an approved model-provider adapter behind AiGateway. Either case requires an architecture exception because the current accepted production direction is Core-backed.

Companion strengths

  • One canonical authority for content, transitions, recovery, audit, export, and deletion.
  • Database transactions match the evidence/stage/version domain instead of emulating them with flat records.
  • The same operation record can support request-bound execution first and durable workers later if tests justify them.
  • Privacy, operator access, retention, and erasure become Brilliant-owned invariants rather than undocumented downstream assumptions.
  • Better foundation for governed profile proposals, corrections, provenance, and future XO continuity.
  • Keeps the user experience and product module in Brilliant Apps while isolating difficult state machinery behind a narrow server-only interface.

Companion constraints and costs

  • Highest initial build and migration risk.
  • Adds a database, migrations, credentials, backup/restore policy, monitoring, incident response, capacity planning, and another failure domain; a worker would add further burden only if selected.
  • Concentrates sensitive data under Brilliant's direct operational responsibility; poor access controls would make the trust posture worse, not better.
  • Requires a sanctioned stateless inference path and verified provider retention/training terms.
  • Creates architectural divergence from the accepted Core-first spine and needs an explicit, documented exception.
  • Risks becoming a second generic workflow engine unless scope is held to Mirror's code-authored lifecycle.
  • Has higher ongoing operating costs; exact database, optional-worker, model, and observability costs are unknown and must be sourced before planning.

Option B is therefore a preferred architecture candidate, not yet a proven compliant production system. Brilliant-owned locality makes erasure and audit governable; it does not itself prove backup erasure, provider deletion, operator controls, or retention. If those proofs fail, the correct outcome is to avoid persisting sensitive production content—not to assume the companion solved it.

Relationship to the existing Mirror app

Recommended disposition: evolve

Treat Agentic Mirror as Mirror's deeper product model, not as a replacement brand or parallel application.

Preserve:

  • canonical /mirror entry and return routes;
  • the current route shell, extended to satisfy the requested four-stage intake/interview/generation/review contract;
  • the Letter as the central artifact and read access to historical Action Plans;
  • Stytch login and Brilliant's server-side authorization boundary;
  • existing artifacts and read access for prior runs;
  • the report/chat surface and the directional future transition into XO;
  • shared capability schemas, UI primitives, flags, and telemetry where they remain sound.

Change conceptually:

  • intake becomes an explicit coverage contract rather than only pre-context;
  • interview stages gain evidence, conflict, sufficiency, and user-advance semantics;
  • generation receives one immutable accepted packet and produces the Letter plus a separately decided next-action artifact;
  • review is separated from generation and cannot mutate without approval;
  • deliverables become explicit versions with corrections, staleness, and acceptance;
  • canonical persistence moves behind a MirrorRuntime interface so native and companion adapters remain conceptually substitutable.

“Evolve” describes continuity of product identity and user experience, not a requirement to preserve internals. Large parts of the existing state and generation implementation may eventually be replaced behind the same surface. Historical artifacts should remain readable; whether to transform or merely grandfather them is a later migration-planning decision.

Why not replace

A separate Agentic Mirror would duplicate a live product journey, confuse the Mirror → XO story, fragment artifacts and chat, and force users to choose between two versions of the same promise. The valuable changes are compatible with the existing experience shape and should strengthen its meaning.

Why not coexist

Permanent coexistence is justified only if the local, accountless, user-controlled writing studio remains a distinct product with a distinct trust promise and arbitrary deliverables. That product is broader than Brilliant Mirror and belongs outside its route/product identity. Within Brilliant Apps, generic multi-workflow capability belongs to Reflow, not a second Mirror.

Recommendation in full

Preferred direction

Evolve the existing Mirror product in place and select Brilliant-owned canonical content authority as the preferred architecture candidate for new sensitive runs, subject to the minimum validations below. Decide colocated/request-bound versus separately deployed/durable execution only after recovery and latency tests.

This choice is not driven by a desire for more infrastructure. It follows from a mismatch between the domain and the current canonical store:

  • Agentic Mirror's central value comes from durable, governable state transitions rather than clever prompting alone.
  • Brilliant's own policy makes hard erasure, access transparency, correction, and ownership part of product correctness.
  • The current Core interface does not prove those properties for the most sensitive record: the interview transcript.
  • A flat-store native build can mimic versioning and recovery, but it cannot manufacture downstream deletion or audit authority.
  • One narrow runtime boundary can preserve Brilliant's product, auth, UI, capability, and future XO shapes while owning the missing lifecycle coherently.

Approve this only as a Mirror-specific, code-authored private runtime, with no generic planner, workflow DSL, or second public app. Preserve AiGateway as the AI-call seam and make Core replication optional and policy-gated. Treat production use as contingent on full-erasure, access-control, and stateless-inference proof; if the candidate cannot prove them, do not persist sensitive production content. The later migration plan should not begin until the architecture exception and data-rights launch bar are explicit.

Strongest non-selected direction

Native Brilliant Apps is a credible, lower-cost architecture, not a fallback in name only. It can add the complete requested journey and already has many recovery patterns needed. Under current policy it is superior for synthetic, ephemeral, or non-production validation, where no sensitive durable content is entrusted to an undeletable store. For production, Core must add verifiable hard deletion and audit plus adequate transactional/durable-operation semantics—or the user must explicitly amend the binding product policy. Once those conditions hold, native should displace the companion recommendation because it would deliver product integrity with the simpler platform shape.

Conditions that would change the recommendation

Change from companion to native

Prefer Option A if all material conditions are demonstrated:

  1. Core can verifiably erase, by owner, task chat, ContextAssets, immutable versions, derived artifacts, indexes/caches, and applicable backups.
  2. Core exposes a user-visible or independently auditable access log and an enforceable protected-write contract.
  3. Core documents retention, provider data handling, payload/pagination limits, durability, recovery objectives, and pricing sufficiently for the product promise.
  4. Core supplies either transactional/CAS publication or a durable idempotent operation ledger adequate for generation and review.
  5. Representative browser-kill and request-timeout tests prove the bounded generation/review chain recovers without duplicate authoritative output.
  6. Personal identity and portability requirements can be satisfied through the current Stytch/Core subject model.

Strengthen the companion recommendation

Brilliant-owned canonical authority becomes even more compelling if Mirror must launch with any of these: a governed durable Leadership Profile, self-service verified deletion, sensitive access auditing, exportable provenance, or cross-run corrections that invalidate downstream artifacts. Long-running/background generation and cross-device event-level resume strengthen the separate case for a durable worker, not the storage decision by themselves.

Reduce the scope or stop the concept

  • If blinded product evaluation shows the evidence/stage/review discipline does not materially improve Letter/Plan usefulness or trust, keep the current Mirror flow and import only small UX controls.
  • If the desired product is an arbitrary local writing studio rather than Mirror onboarding, it does not belong inside Mirror; keep it separate or route generic workflow work to Reflow.
  • If neither Core nor an approved companion can meet the data-rights launch bar, do not persist a Leadership Profile or imply long-term governed memory.

Decisions required before a migration-ready plan

The later planning assignment needs the user to decide these points explicitly:

  1. Product identity: Is this a deeper Mirror onboarding ritual or a generic writing/workflow studio?
    Recommendation: Mirror-specific onboarding; leave generic workflows to Reflow.

  2. Disposition: Replace, evolve, or coexist?
    Recommendation: Evolve /mirror in place; do not create a permanent second experience.

  3. Canonical architecture: Native Core/ContextAssets after its gaps close, or a Brilliant-owned canonical runtime?
    Recommendation: Brilliant-owned authority as the preferred candidate, contingent on full-erasure and stateless-AI proof.

  4. Architecture exception: Is a narrow Mirror-specific database/runtime exception to the Core-first spine authorized?
    Recommendation: Authorize investigation and planning only after its scope and exit criteria are recorded; do not authorize a general platform fork.

  5. Data-rights launch bar: Which record classes must support export, audit, retention disclosure, and verified deletion before launch?
    Recommendation: Include transcripts, evidence, frozen packets, every artifact/review version, profile proposals, caches/indexes, and provider-held content.

  6. Deliverable contract: What follows the Letter for new runs?
    Recommendation: Keep the Letter central and historical Action Plans readable. Decide the revisable next-action artifact separately; do not broaden Mirror to arbitrary deliverables.

  7. Profile policy: Persist no profile, proposals only, or approved durable facets?
    Recommendation: No silent writes; proposals only after the governance contract is proven, then explicit user approval.

  8. Review depth: One bounded judge/revision pass or repeated iterative review?
    Recommendation: Validate one bounded pass first; expand only if it produces measurable value.

  9. Historical continuity: Must existing Mirror runs remain readable under the current surface?
    Recommendation: Yes. Grandfather read access; decide transformation only in the later migration plan.

  10. Local Agentic Mirror future: Does its accountless, local-first, arbitrary-writing proposition remain separately valuable?
    Recommendation: If yes, keep it a distinct product; do not make Brilliant Mirror carry both promises.

  11. Execution topology: Must generation/review survive a dead request without user-triggered replay?
    Recommendation: Start the later plan from request-bound operation records; authorize a durable worker only if failure and latency validation require it.

Decision-ready conclusion

  • Does the concept belong in Brilliant Apps? Yes—its evidence, human authority, frozen-context, versioned-review, and acceptance model materially strengthens Mirror.
  • Should it replace the current Mirror app? Evolve the current product identity and surface; replace internals selectively behind that surface. Do not create a second Mirror.
  • Should it be platform-native or use a companion? Prefer a narrowly scoped Brilliant-owned canonical authority, conditionally. Use native for non-production validation or after Core proves the missing guarantees. Decide durable-worker topology separately.
  • Proceed to migration planning now? Proceed only after the user makes the eleven decisions above and the smallest decisive validations establish the Core deletion boundary, approved stateless inference path, and companion trust boundary.
