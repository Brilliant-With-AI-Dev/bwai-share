Brilliant Apps Chat: system and Core data flows

A source-grounded account of what enters Chat, how Core carries and stores it, what returns to the browser, and where the current design is incomplete.

Orientation

Chat is an authenticated, desktop-first workspace inside Brilliant Apps. Core owns conversation execution and two distinct storage planes. The Next.js app owns the user experience, record shapes, authorization checks, and browser-side orchestration.

Today

Behavior is distributed across browser hooks, API routes, SDK packages, Core contracts, and hidden context assets.

After

This page gives one trace from user input through Core and back, with route, storage, and feature references.

Why

A shared map makes product review, privacy review, debugging, and future migration decisions less speculative.

Plain-English summary

The browser never calls Core directly for Chat. It calls the Brilliant Apps server. The server authenticates the member, checks the release flag, and uses shared SDK clients. Core retains the actual conversation in a task step. Separately, Core context assets hold Chat's thread, project, attachment, event, and artifact records. The browser receives sanitized views and keeps transient workspace state in memory.

CONFIRMED Directly supported by source, tests, or work records. INFERRED A code-derived consequence that was not measured. UNKNOWN The available contract does not answer it.

TL;DR

  • Chat is gated by authentication and release.chat-app.
  • Core task-step chat stores system, user, and assistant turns.
  • User-scoped Core context assets store Chat application records.
  • Attachments become extracted text before model submission.
  • Artifact discovery is heuristic, then server-verified.
  • Metadata commands are explicit slash commands, not model tools.
  • Production exposure and product direction remain unresolved.

Gate sequence

  1. /chat calls the release flag and returns 404 when off.
  2. The app-wide Stytch guard requires an authenticated session.
  3. Every Chat API request checks the same flag first.
  4. The API derives organization and member ownership from Stytch.
  5. A user-scoped store and owner-scoped repository are created.

Data flows

The most important distinction is between conversation history and Chat application records. Both live behind Core contracts, but they use different APIs and record shapes.

1. Create a thread

Profile + selected completed Mirrors + optional project
  -> POST /api/chat/threads
  -> validate owner-scoped context
  -> Core: create task
  -> Core: inject system turn into step-01, no LLM submission
  -> Core context asset: write chat/thread/v1/<threadId>
  -> browser: receive public thread and select it

The server always tries to use the current profile when available. Selected Mirrors must be completed, owned, and listed in the member's manifest. Profile and Mirror content is clipped, template syntax is neutralized, HTML is escaped, and the result is wrapped as data inside a system prompt. The prompt forbids treating this data as instructions or mutating it.

The Core task ID and fixed step-01 are then referenced by the Chat thread record. Core task creation and initialization happen before the record write.

Sources: apps/web/app/api/chat/threads/route.ts:39-63; apps/web/lib/chat/runtime.ts:28-49,116-134; apps/web/lib/chat/context.ts:55-167.

2. Send a message and stream a reply

Draft + selected attachment IDs
  -> browser uploads files, if any
  -> optimistic user message
  -> POST /api/chat/threads/<id>/messages
  -> load owned thread and extracted attachment text
  -> write attachment consumption events
  -> Core inject-turn: user content, submitToLlm=true
  -> raw Core SSE returns through Next.js
  -> @bwai/chat-engine parses text and envelope
  -> browser commits assistant display
  -> patch local searchText
  -> optional artifact and automatic-title follow-ups

Attachment text is escaped and wrapped with a warning that it is untrusted data. The user message is also encoded before the shared Core client submits it. The server returns Core's SSE body without a hand-written event parser. The browser uses @bwai/chat-engine and aborts after 45 seconds without stream activity.

Core commits the user and assistant turns to the task step. Search text, artifacts, and title are follow-up writes. A successful reply can therefore exist even when one of those derived writes fails.

Sources: apps/web/app/api/chat/threads/[threadId]/messages/route.ts; apps/web/lib/chat/runtime.ts:136-185; packages/sdk/src/core-backend.ts:443-486,526-573.

3. Reopen history

GET /api/chat/threads/<id>
  -> read thread + events from user-scoped context assets
  -> Core typed client: read task, then step chat
  -> verify task and expected template
  -> keep user and assistant turns
  -> strip attachment wrappers and assistant envelopes
  -> attach public artifact and attachment metadata
  -> browser renders committed transcript

Historic attachment chips are rebuilt from attachment metadata. Extracted text is not returned in the public attachment shape. Core remains the authority for committed conversation history.

4. Update metadata

Rename, pin, favorite, status, tags, description, notes, project, archive, delete, and restore do not mutate the base record. Each produces an immutable event context asset. Reads sort events by timestamp and ID, then fold them over the base thread. Later same-field events win. A manual title prevents a late automatic title from replacing it.

Source: apps/web/lib/chat/repository.ts:80-89,137-184.

5. Extract and persist an artifact

The browser marks an assistant reply as a candidate when it contains a long fenced block or substantial structured Markdown. It then reconciles against committed Core history and sends only the source message ID. The server reloads history, verifies that committed assistant message, runs detection again, clips content to 20,000 characters, and writes a deterministic immutable artifact record.

6. Dictate with voice

Microphone permission
  -> POST /api/voice/token with Stytch token
  -> Brilliant Apps catch-all proxy
  -> Core voice-token endpoint
  -> token returns to browser
  -> browser opens Deepgram WebSocket
  -> MediaRecorder sends microphone chunks
  -> transcript updates the composer draft

Voice is dictation only. It is not a Core conversation turn until the member sends the resulting text. Chat does not provide text-to-speech or read-aloud output.

Sources: packages/voice/src/useVoiceInput.ts:266-280,322-394,492-498; apps/web/app/api/[...path]/route.ts:35,138.

Storage model

Core holds durable state. The browser holds working state. Chat uses the Core context-asset store as an owner-scoped record database.

Conversation plane

Core task and step-01 store the initialization prompt plus committed user and assistant turns.

Application plane

Hidden user-scoped context assets store threads, events, projects, attachments, and artifacts.

Working plane

React memory stores drafts, selection, streaming text, filters, retries, and local command replies.

Every record includes organization and member ownership. Reads filter on both. Writes use type: state and visible: false. The SDK sends machine credentials plus X-On-Behalf-Of delegation for context-asset access.

Limits enforced by Chat

  • Five live attachments per thread.
  • Ten megabytes per uploaded file.
  • Fifty thousand extracted characters per attachment.
  • Eighty thousand selected attachment characters per turn.
  • Twelve artifacts per thread.
  • Twenty thousand characters in thread search text.
  • Twelve tags; 32 characters per tag.
  • Description 500 characters; notes 4,000 characters.

Browser persistence

Chat does not persist the active thread, draft, filters, retry candidate, or selected artifact. It writes two small voice hints: composer mode in session storage and an authentication-failure flag in local storage. Durable conversation and Chat records stay server-side.

Error boundary

Upstream 401, 403, and 404 responses are normalized. Other platform and configuration failures become 502 responses. Internal details are not returned to the browser.

Feature-by-feature behavior

Workspace and navigation

On load, the browser fetches thread history and context in parallel. The history sidebar supports search, grouping, projects, recent threads, pinning, and filters for active, waiting, done, archived, and deleted states. Search is local over title, search text, description, notes, status, tags, and project title.

The active thread is not encoded in the URL. Navigation epochs abort stale loads, streams, retries, and artifact reconciliation. Changing threads clears draft attachments and artifact selection.

Composer, streaming, stopping, and retry

Sending lazily creates a thread, uploads files sequentially, appends an optimistic user message, and streams assistant text. Stop aborts the browser fetch. The textarea remains editable during a stream.

Retry first reconciles with committed Core history. It never duplicates a reply already committed. If only the user turn was committed, Chat refuses to repeat it and asks for a follow-up. Post-commit aborts are not retried.

Thread metadata

The header supports title, project, pin, favorite, status, tags, description, notes, archive, trash, and restore. Browser writes are serialized through one mutation queue. Tags, description, and notes save on blur.

A separate naming capability proposes the first title after a successful initial reply. It creates a fresh Core completion task. Failure uses a sanitized first-line fallback. A manual title always wins.

Slash commands

Supported commands cover help, show, notes, rename, pin, favorite, archive, restore, status, tags, description, notes, and project assignment. Invalid command syntax never reaches Core's model. Deleted threads allow only help, show, and restore.

Commands are normal API mutations, not tools available to the assistant. Their acknowledgment messages are appended only in browser memory and disappear on reload.

Attachments

The browser accepts TXT, Markdown, PDF, and DOCX by picker or drag-and-drop. The server requires matching extension and MIME, parses text with format-specific readers, trims and clips it, then stores it in a hidden context asset.

Selected attachment text is treated as untrusted data in the model turn. Consumption events enforce one concurrent use. The public transcript receives names and types, not extracted text.

Artifacts

Candidate replies show an artifact card and open a side panel, or a modal below 1,280 pixels. The panel renders Markdown and supports copy and safe-filename download. Source-message verification prevents a browser from persisting arbitrary content.

Context selection

Before thread creation, Chat shows the current profile and lets the member select completed Mirrors with bounded previews. Profile use is automatic when available. The context selection becomes immutable after creation.

Projects

Members can create projects after a thread exists and assign threads by header control or slash command. Server routes also support rename and soft deletion, including detaching threads. The current browser client and interface do not expose those two project administration actions.

Voice dictation

Voice checks browser capabilities, obtains microphone permission, gets a short-lived token through the authenticated server proxy, and streams media to Deepgram. Interim and final transcript text updates the draft. The user still chooses whether to send it.

Deliberate exclusions

The current scope excludes web search, general end-user tools, action-taking integrations, live conversational voice, text-to-speech, and direct external model providers. Files are model context, not callable tools.

External and trust boundaries

Boundary Credential or trust Data crossing Control
Browser to Next.js Stytch member session Drafts, file bytes, IDs, metadata Flag, session, schema, ownership checks
Next.js to Core tasks User JWT or M2M plus delegation System context, turns, history reads Typed shared clients and task verification

Browser to Deepgram Short-lived Core-minted token Live microphone media; transcript events Permission and explicit dictation control

Selected profile and Mirror material is a retrieval-only snapshot. It is sanitized and labeled as data before entering the system prompt. Uploaded file text receives a similar untrusted-data wrapper. These measures reduce instruction injection risk without claiming that arbitrary content is harmless.

This explanation stops at the published SDK and application contracts. It did not inspect the private Core implementation repository. Core's internal database schema, indexes, retention jobs, and provider routing are therefore outside the confirmed boundary.

Known issues, incomplete areas, and gaps

Confirmed gaps are directly visible in source or work records. Inferences identify credible consequences, not measured incidents.

CONFIRMED Production remains dark

The release registry enables Chat for development and Preview but disables production. The work remains on a feature branch. Impact: users cannot rely on this surface in production.

CONFIRMED Product direction is unresolved

The work record marks a conflict with the thread-oriented product vision and requires owner approval before merge. Impact: implementation quality alone cannot authorize release.

CONFIRMED Project administration is incomplete

Server routes implement project rename and delete, but the browser client and interface do not expose them. Projects can only be created after a thread exists. Impact: members cannot finish normal project housekeeping.

CONFIRMED No thread deep links

Active selection lives only in React memory. Impact: reload loses location; a specific thread cannot be bookmarked or shared.

CONFIRMED Several states are memory-only

Drafts, retry candidates, filters, selected artifacts, and command acknowledgments disappear on reload or navigation. Impact: interrupted work is not fully recoverable.

CONFIRMED Context is fixed at creation

Existing threads cannot add or remove profile or Mirror context. An available profile is automatic, with no browser opt-out. Impact: member control is limited and old conversations cannot adopt new context.

CONFIRMED Search can become stale

The browser maintains a clipped search-text field after a reply. It is not a server-derived full-transcript index. Impact: a failed metadata patch can leave a saved reply undiscoverable through local text search.

CONFIRMED Artifact detection is heuristic

Core returns no structured artifact marker. Chat infers one from long code fences or substantial Markdown, then performs extra reconciliation. Impact: valid artifacts can be missed or ordinary replies can be offered as artifacts.

CONFIRMED Deletion is soft only

Thread and project deletion writes events. No permanent deletion route exists. Impact: underlying Core data remains stored and restorable.

CONFIRMED Metadata conflicts use last-event-wins

Events sort by creation time and ID. Same-field concurrent edits have no explicit conflict response. Impact: one successful edit can silently supersede another.

CONFIRMED Stream timeouts differ

The browser has a 45-second idle timeout while the server permits up to 300 seconds. Impact: a long silent generation can abort client-side before server duration expires.

CONFIRMED Some failure feedback is coarse

Tags, description, and notes save on blur with a shared error surface. Artifact copy lacks the rejection handling used by reply copy. Impact: recovery is unclear for individual failed actions.

INFERRED Full asset scans may scale poorly

Several thread, project, and artifact operations call the user-scoped store list and filter in application code. Impact: latency and Core reads may grow with a member's total context-asset count. No threshold was measured.

INFERRED Failed creation can orphan a Core task

Task creation and system-turn injection precede the thread record write. No compensating task deletion is visible. Impact: a later validation or storage failure can leave a Core task unreachable from Chat.

INFERRED Immutable writes are not atomic

The repository enforces immutability with read-then-write over a store without compare-and-set. Impact: concurrent writes to the same deterministic key could race, although unique IDs make most collisions unlikely.

INFERRED Aborted attachment flows may leave records

Attachment consumption is released only when the Core call throws before returning a stream. A later browser abort does not show a server release path. Impact: retry can require a new upload while hidden attachment records remain.

UNKNOWN Core internals and retention

Published contracts do not specify internal indexes, physical tables, retention schedules, or cleanup for naming tasks and hidden Chat assets. Impact: this report cannot establish storage cost, retention duration, or deletion SLA.
